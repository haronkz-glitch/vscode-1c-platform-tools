# 09 - События, инвалидирование и VS Code Problems

## Единый маршрутизатор файловых изменений

**ID-001-09-0001** - Файловые, проектные и конфигурационные события собираются в одном координаторе Code Style. Обработчики не выполняют проверки напрямую, а разрешают затронутый project/source/target, вызывают инвалидирование Store и передают coalesced scope Scheduler.

**ID-001-09-0002** - Для BSL подключить `onDidSaveTextDocument` и `onDidChangeTextDocument` (dirty => немедленный stale), а также ограниченные FileSystemWatcher для создания/изменения/удаления файлов вне активного редактора. Не создавать watcher на каждое правило или metadata-объект.

**ID-001-09-0003** - Для метаданных использовать штатный `onDidChangeMetadataFiles` из `metadataFileChanges.ts` для записей md-sparrow и соответствующие watcher/события VS Code для внешних изменений. Сигнал изменения layout `onDidChangeProjectLayout` и `onDidChangeProjects` обрабатывать отдельно от содержимого одиночного файла.

**ID-001-09-0004** - `projectLayoutWatch.ts` отслеживает изменения раскладки, но не заменяет наблюдение за изменениями всех `.bsl`. Подключить недостающий ограниченный watcher, не переписывая существующий общий поток проектов.

**ID-001-09-0005** - Переименование и удаление через VS Code обрабатывать с помощью `workspace.onDidRenameFiles` / `onDidDeleteFiles`, а изменения извне - парными create/delete событиями watcher. Не рассчитывать на доступность приватного emitter перемещений из `metadataFileChanges.ts`.

**ID-001-09-0006** - При Save + FileSystemWatcher + md-sparrow уведомлениях одной версии объединять события, не формировать параллельные независимые полные проверки. Новая версия того же файла должна пройти отдельное инвалидирование даже во время debounce.

**ID-001-09-0007** - Изменение состава проекта/раскладки переразрешает проектные границы, источники и цели; не очищать результаты по неподтверждённой неполной snapshot. Смена UI-текущего проекта не очищает чужие диагностики.

**ID-001-09-0008** - При `scanOnSave=false` всё равно помечать изменённые/удалённые результаты устаревшими; автоматическое повторное сканирование по изменениям не запускать. В этом состоянии новый актуальный результат появится после явного запроса будущего этапа.

## Публикация в Problems

**ID-001-09-0009** - Создать отдельную `vscode.DiagnosticCollection` с именем `1c-code-style`; существующую `1c-syntax-check` не изменять, не очищать и не переиспользовать.

**ID-001-09-0010** - `CodeStyleProblemsPublisher` подписывается только на события IssueStore и запрашивает его актуальные issues. Публикация не запускает SourceProvider, RuleRegistry, Scheduler, md-sparrow и не меняет состояние замечаний.

**ID-001-09-0011** - Каждый Issue преобразуется в `vscode.Diagnostic`: URI существующего файла, валидированный Range, `DiagnosticSeverity`, сообщение, `source='1C Code Style'`, `code=ruleId` и при наличии `relatedInformation`. Дополнительные сведения об исправлении сейчас не превращаются в CodeAction.

**ID-001-09-0012** - При изменении результатов группировать по URI и пересчитывать объединённый актуальный набор **всех** projectKey/ruleId для затронутых файлов. Не писать `set(uri, diagnosticsFromOneRule)`, если это сотрёт диагностики остальных правил.

**ID-001-09-0013** - Если для URI больше нет актуальных замечаний после успешной проверки, удаления, выключения правила или инвалидирования - вызвать `set(uri, [])` или `delete(uri)`; старая проблема должна исчезнуть сразу, не дожидаясь полного сканирования.

**ID-001-09-0014** - Если результат содержит только stale/incomplete/error, не показывать его как актуальную диагностику. Причину отсутствия полноты хранить в ScanResult/IssueStore для будущих интерфейсов, не добавляя в Problems псевдоошибки инфраструктуры.

**ID-001-09-0015** - Publisher не фильтрует по текущему выбранному проекту: все актуальные проблемы открытых проектов могут одновременно отображаться в Problems. Фильтрация панели будет реализована позднее на уровне общего IssueStore.

**ID-001-09-0016** - Не публиковать нарушения для виртуальных файлов или несуществующих fallback URI. Ошибку получения локации обнаруживает Engine/SourceProvider; Publisher не изобретает путь или диапазон.

**ID-001-09-0017** - Publisher предоставляет dispose, освобождает event subscription и DiagnosticCollection; поздние события после деактивации не должны восстанавливать очищенные диагностические записи.

## Логи и внешнее поведение

**ID-001-09-0018** - Использовать `logger.scope('code-style')` для сообщений об ошибках источника, отмене, incomplete, изменении очереди и критических сбоях. Не создавать отдельный Output Channel ради Code Style.

**ID-001-09-0019** - В Task #1 не регистрировать новые команды refresh/check/clear и не показывать всплывающие уведомления при каждом штатном файловом событии. Некритические технические ошибки сохраняются для службы/лога, но не прерывают другие функции Platform Tools.

**ID-001-09-0020** - Ошибки независимой подсистемы не должны ломать текущую публикацию syntax-check или другие подписки расширения. Не вмешиваться в файлы `syntaxCheckDiagnostics.ts` / `registerDiagnosticsFeature.ts`.

**ID-001-09-0021** - При завершении расширения вместе с Scheduler освобождать FileSystemWatcher, таймеры, event emitters и DiagnosticCollection; одинаковая подписка не должна создаваться повторно после переключения проекта.
