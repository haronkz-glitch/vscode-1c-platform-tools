# 10 - Слой действий и внутренний CodeStyleService

## Единая точка доступа

**ID-001-10-0001** - `CodeStyleService` создаётся один раз за время жизни расширения как фасад Task #1 и будущая точка доступа для панели и MCP. Он владеет экземплярами Registry, Engine, Planner/Scheduler, Store, Settings, SourceRegistry и Publisher через явные зависимости.

**ID-001-10-0002** - Сервис предоставляет внутренние операции: получение списка определений/настроек, запуск проекта/файла/списка целей, чтение сохранённых замечаний с общими фильтрами, получение состояния выполнения и подписку на изменения. Эти вызовы не должны зависеть от наличия зарегистрированного ActionDefinition.

**ID-001-10-0003** - Сервис фиксирует при каждом запуске явный projectKey и scope. Он не читает «активный редактор» и не выбирает `currentRoot()` как скрытый default; будущие адаптеры MCP/панели передадут target извне.

**ID-001-10-0004** - Сервис не дублирует Engine/Store и не формирует вторые хранилища для MCP/панели; фасад делегирует реальные операции соответствующим внутренним компонентам и возвращает нормализованный результат.

**ID-001-10-0005** - Внутренние фоновые события VS Code вызывают ScanPlanner через сервис/координатор напрямую, не регистрируют фиктивные ActionDefinition и не маршрутизируют каждое сохранение через ActionDispatcher.

**ID-001-10-0006** - Один сервис не должен ссылаться на ActionDispatcher, который для запуска обработчиков обратно вызывает сам CodeStyleService и образует цикл. В ActionContext передавать минимальные абстракции функций/портов, а не полный владеющий объект.

## Определение и регистрация действий

**ID-001-10-0007** - `ActionDefinition` содержит постоянный уникальный actionId, короткие title/description, декларацию эффекта (`read`, `settingsWrite`, `sourceWrite`), схему/валидатор входных параметров и обработчик, возвращающий общий структурированный результат.

**ID-001-10-0008** - `ActionRegistry` поддерживает регистрацию, получение, список, проверку уникальности и корректности обязательных полей. Дубликат actionId является ошибкой, а не тихой заменой.

**ID-001-10-0009** - `actions/registerActions.ts` является единственной production-точкой статической регистрации прикладных действий. В Task #1 он не регистрирует ни одного действия; даже `listRules`, `check`, `getIssues` и `fix` реализуются только в последующих задачах.

**ID-001-10-0010** - `ActionDispatcher` выполняет последовательность: найти actionId, проверить параметры/схему, проверить допустимость и полномочия эффекта, создать ограниченный ActionContext, вызвать обработчик, нормализовать результат или ошибку. Нет переключателей `switch(actionId)` по конкретным операциям.

**ID-001-10-0011** - Маркер `effect='sourceWrite'` лишь описывает класс действия и не авторизует изменение файлов. Будущие sourceWrite-операции требуют отдельной явной политики доступа и согласованного пользовательского разрешения; в Task #1 не создавать путь записи.

**ID-001-10-0012** - Не добавлять отдельные действия на каждое правило, формат источника или окно. Например, универсальный `getIssues` в будущем применяет общие фильтры IssueStore ко всем правилам, а не вызывает особую функцию `getCommonModuleIssues`.

## Контракты внешнего обмена

**ID-001-10-0013** - Внутренняя граница Dispatcher использует JSON-совместимые DTO: project/source/target представлены строками, фильтры - простыми значениями, ошибки - кодом и текстом. Классы `vscode.Uri`, `TextDocument`, `Error` и функции не переходят наружу.

**ID-001-10-0014** - Отдельно описать `target/scope` для определения анализируемого проекта или файлов и `filter` для выборки IssueStore. `getIssues` не должен неявно запускать анализ, а `check` не должен автоматически выполнять `fix`.

**ID-001-10-0015** - В результате каждого action-вызова различать успешность операции, данные, неполноту и техническую ошибку. Исключения внутри обработчика перехватывает Dispatcher, логирует и возвращает предсказуемый результат без утечки стека.

**ID-001-10-0016** - Универсальные события сервиса (`issuesChanged`, `settingsChanged`, `scanStateChanged`) содержат минимальные сведения, необходимые подписчику для выборки обновлённого состояния. В Task #1 не вводить форматы Webview postMessage или MCP toolParams.

**ID-001-10-0017** - Отсутствие действия в пустом ActionRegistry возвращает контролируемое `unknownAction`, а не приводит к автоматическому исполнению внутреннего метода сервиса. В Task #1 этот путь можно реализовать без фиктивных команд.

**ID-001-10-0018** - Обработчики будущих действий используют общий Read-only API Settings/Store/Planner и не обращаются напрямую к VS Code UI. Выбор пользовательских кнопок, команда MCP и проверка полномочий внешнего шлюза остаются транспортными обязанностями следующих этапов.

## Жизненный цикл и границы Task #1

**ID-001-10-0019** - Сервис предоставляет dispose, отменяет назначенные запуски, снимает подписки и освобождает owned components ровно один раз. Нельзя уничтожать общие singleton-ресурсы Platform Tools, которыми владеют другие подсистемы.

**ID-001-10-0020** - В Task #1 не реализовывать смену настроек по внешнему action, Webview-панель, CodeActionProvider, редактирование исходников, MCP-команды или отдельный MCP-сервер. Реальный результат - готовая расширяемая внутренняя диспетчеризация с пустым registry.

**ID-001-10-0021** - Следующие этапы могут добавить универсальные операции через реестр без изменения контрактов уже существующих проверок. Смена протокола MCP/панели не должна изменять Engine или IssueStore.

**ID-001-10-0022** - Бизнес-логика активного списка правил, фильтрации замечаний и проверки не переопределяется в Dispatcher: он только валидирует/вызывает действие, а его обработчик делегирует существующим сервисам.
