# 04 - Поставщики BSL и метаданных

## Реестр и протокол поставщика

**ID-001-04-0001** - `SourceRegistry` регистрирует ровно одного ответственного поставщика для каждого поддержанного `SourceKind`, запрещает дубли и предоставляет выбор по виду источника. На этапе Task #1 действительно подключены BSL и metadata; для forms, queries и rights предусмотрены типы/возможность будущей регистрации, но не пустые поставщики, изображающие успешный анализ.

**ID-001-04-0002** - У поставщика разделить `enumerate(scope)`, выдачу дешёвых `TargetDescriptor`, и `read(target, cancellation)`, выдачу данных/снимка по запросу. Независимо от имён методов контракт позволяет отобрать правила по descriptor до чтения содержимого.

**ID-001-04-0003** - `enumerate` возвращает не только цели, но и признак полноты, явные ошибки/неподдерживаемые корни и версию перечня. Пустой полностью прочитанный перечень означает «целей нет»; ошибка, отмена или усечение означает incomplete, а не нулевой результат.

**ID-001-04-0004** - Поставщик не знает ID конкретных правил и не выбирает их по специальным условиям. Предварительный отбор осуществляется Engine через `supports` и `supportsTarget` определений из RuleRegistry.

**ID-001-04-0005** - Загрузка одного подробного снимка цели в рамках одного запуска разделяется между всеми применимыми правилами с помощью memoized Promise; повторное чтение для каждого правила запрещено. При ошибке общее чтение остаётся ошибочным для всех зависящих проверок, а не заменяется пустым объектом.

**ID-001-04-0006** - `TargetDescriptor` фиксирует файл и источник, но отсутствие файла у виртуальной сущности недопустимо для публикации: заранее обозначить реальный fallback-файл. Если подходящего существующего файла нет, вернуть unsupported/incomplete, не выдумывать URI.

**ID-001-04-0007** - Связь двух уровней данных обязательна: каждый `read` удостоверяется, что цель по-прежнему относится к тому же sourceKey и projectKey и данные не устарели; изменения между enumerate/read/commit проверяет механизм актуальности из `06-scheduler.md` и `07-issue-store.md`.

## BSL: перечисление и чтение

**ID-001-04-0008** - Получать разрешённые каталоги BSL из `ProjectLayout` и границ проекта из `03-projects.md`, в том числе конфигурации, расширения, тестовые источники, внешние обработки/отчёты. Можно использовать `vscode.workspace.findFiles` с относительными шаблонами внутри конкретного корня либо собственный ограниченный обход; не искать `**/*.bsl` глобально по workspace.

**ID-001-04-0009** - Не исключать `Ext` автоматически: в 1C:Конфигуратор реальные модули расположены, например, в `CommonModules/Имя/Ext/Module.bsl`. Исключения обнаружения других проектов из `projectLayout.ts` не переносить бездумно на BSL-обход.

**ID-001-04-0010** - Исключать файлы чужих подпроектов, каталоги вне source roots, служебные результаты сборки и заданные Platform Tools исключения. Если применённый glob/провайдер возвращает неполный список, это обязательно помечается incomplete, без общей очистки непосещённых целей.

**ID-001-04-0011** - Внутренний BSL-ключ цели привязан к нормализованному абсолютному пути в сочетании с projectKey/sourceKey; форма имени модуля и каталог `Ext` не создают дополнительных синтетических целей для одного файла.

**ID-001-04-0012** - В `read` возвращать исходный текст и локацию без изменений содержимого, кодировки, CRLF/LF и BOM. Не делать форматирование и не создавать отсутствующие `.bsl` через `ensureBslModuleFile`: такая функция пишет файлы и запрещена для линтера.

**ID-001-04-0013** - Если `TextDocument.isDirty`, немедленно инвалидировать ранее проверенный снимок и не читать старый файл с диска как актуальный. В Task #1 текущий режим - анализ после сохранения; повторно назначать проверку после `onDidSaveTextDocument`.

**ID-001-04-0014** - Если документ открыт и сохранён, его `getText()` допускается как согласованный источник; иначе чтение файла выполняется через read-only API. Перед публикацией проверить версию данных с учётом сохранения/изменения файла.

**ID-001-04-0015** - Ошибка чтения отдельного файла помечает соответствующую цель incomplete/error и не влияет на другие прочитанные файлы. Удалённый файл должен инвалидироваться даже если попытка прочитать его завершилась ошибкой.

## Метаданные: дерево, фильтр, подробные свойства

**ID-001-04-0016** - Дерево получать через `loadProjectMetadataTree(context, root)` из `metadataTreeService.ts` лишь когда выбранное metadata-правило действительно применимо к проекту. Не загружать runtime md-sparrow при пустом RuleRegistry, выключенном линтере либо отсутствии metadata-правил.

**ID-001-04-0017** - Для каждого `MetadataSourceDto` использовать `configurationXmlRelativePath`, `metadataRootRelativePath` и `groups/subgroups/items`. Для `MetadataItemDto` использовать `relativePath`, `objectType` и прочие данные дерева; относительные пути проверяются внутри проектных/source границ. Помимо вложенных объектов, для самой конфигурации и каждого расширения выдавать по одной отдельной корневой metadata-цели со sourceKey соответствующего источника, устойчивым targetKey и реальным файлом из `configurationXmlRelativePath`. Descriptor явно различает корень конфигурации/расширения и вложенный объект, чтобы `supportsTarget` мог отобрать их до чтения свойств. Корни обслуживаются тем же metadata-поставщиком, без отдельного SourceKind.

**ID-001-04-0018** - Первый этап metadata - перечислить краткие цели; второй - по `supportsTarget` оставить только потенциально подходящие цели, например `CommonModule` или корень конфигурации/расширения; третий - читать свойства выбранных целей. Не читать подробные свойства всех целей без такого отбора независимо от используемой операции md-sparrow.

**ID-001-04-0019** - Для правила, которому достаточно данных дерева, RuleContext предоставляет descriptor и не инициирует подробное чтение. Для правила, которому нужны свойства, ленивый read выполняет `ensureMdSparrowRuntime(context, root)` и `runMdSparrowParamsRead` с `{cwd:root, token}`. Поставщик выбирает параметры по виду цели: для вложенного объекта - `{op:'cf-md-object-get', objectXml, schemaVersion}`, для корня конфигурации или расширения - `{op:'cf-configuration-properties-get', configurationXml, schemaVersion}`. Правило не выбирает команду md-sparrow и не обращается к ней напрямую. Тестами проверить перечисление корней, выбор операции для конфигурации, расширения и вложенного объекта и отсутствие подробного чтения отсеянных целей.

**ID-001-04-0020** - Реальные пути `objectXml` и `configurationXml` берутся из дерева и layout, а не строятся только из отображаемого названия. Учитывать, что у 1C:EDT описание объекта в `.mdo`, а у 1C:Конфигуратор в `.xml`; проверять существование файла и допустимость по границам до вызова md-sparrow.

**ID-001-04-0021** - Версию схемы для вызова md-sparrow определять согласно исходнику: использовать сведения дерева только при их пригодности для конкретного источника, иначе существующий `mdSparrowSchemaFlagFromConfigurationXml`. Не предполагать, что версия основной конфигурации всегда подходит расширениям и внешним объектам.

**ID-001-04-0022** - Полученный JSON обрабатывается как типизированное DTO выбранной цели, без насильственного сплющивания типов в `scalars`. Свойства общих модулей находятся в `commonModule`, но интерпретация этих значений и профилей принадлежит будущему правилу, не поставщику.

**ID-001-04-0023** - Использовать кэш `runMdSparrowParamsRead` и штатную политику runtime. Новый общий дисковый кэш DTO не создавать; внутренняя memoization ограничена жизненным циклом запуска, чтобы исключить рассинхронизацию с существующим кэшем.

**ID-001-04-0024** - Проверка отмены проходит от Scheduler к реальному `vscode.CancellationToken` у md-sparrow; если общий движок пользуется `AbortSignal`, адаптер связывает их с освобождением подписки. Если операция физически не прерывается, её результат запрещено принимать после отмены.

**ID-001-04-0025** - При `schemaSupported === false` или ошибке md-sparrow не объявлять metadata-источник пустым. Возвращать unsupported/incomplete/error, не удалять старые замечания за непроверенные цели.

**ID-001-04-0026** - Когда основная конфигурация отсутствует и `loadProjectMetadataTree` не может получить дерево именно по причине отсутствия конфигурации, предусмотреть перечисление внешних обработок/отчётов из `ProjectLayout`. Опорная логика уже есть в `metadataTreeView.ts` (`externalSourcesFromLayout`); использовать её без зависимости от UI-состояния, при необходимости через небольшой независимый helper.

**ID-001-04-0027** - Резервный обход внешних объектов не должен скрывать произвольную ошибку JVM, повреждённое дерево или устаревшую схему. Публиковать только действительно обнаруженные и доступные цели и честно отмечать неполноту неразрешённых частей проекта.

## Чтение, версии и расширение источников

**ID-001-04-0028** - В снимке источника сохранять фактически прочитанную версию: для BSL - редакторскую/файловую версию, для metadata - доступную проверяемую версию файла/дерева. При необходимости использовать `metadataFileVersion` или согласованный fingerprint; не считать время старта запуска эквивалентом версии содержимого.

**ID-001-04-0029** - При частичном событии изменения метаданных связать путь с объектом/source по последнему достоверному дереву или обновлённой раскладке. Если точная цель не определена, назначать безопасный ограниченный переобход соответствующего metadata-source и не очищать непосещённые цели.

**ID-001-04-0030** - Источник обязан различать `отсутствует`, `не поддерживается`, `не прочитан` и `прочитан без нарушений`. Технические ошибки, отмены и неполнота передаются наверх структурированно, а не сообщением в stdout или пустым массивом.

**ID-001-04-0031** - Дополнительные поставщики форм/запросов/прав подключаются позднее через тот же SourceRegistry, не требуют редактирования Engine или IssueStore. В Task #1 их алгоритмы, сканеры и фиктивные данные запрещены.
