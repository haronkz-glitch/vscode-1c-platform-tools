# 11 - Интеграция в Platform Tools и готовность

## Файлы и сборка

**ID-001-11-0001** - Основной production-код Task #1 размещается в `src/features/codeStyle/` с логическими группами `core`, `sources`, `rules`, `actions`, `presentation` и входом `registerCodeStyleFeature.ts`. Разделение по файлам может быть компактнее, если сохранены самостоятельные границы ответственности.

**ID-001-11-0002** - Существующие исходники менять минимально: `src/app/bootstrapApp.ts` для регистрации и dispose, `package.json` для общих настроек и, при необходимости, правил активации. Любой иной изменённый старый файл требует технического обоснования; не выполнять широкое форматирование стороннего кода.

**ID-001-11-0003** - Не менять `syntaxCheckDiagnostics.ts`, `registerDiagnosticsFeature.ts`, `channelServer.ts`, `mcpCommandPolicy.ts`, существующие имена команд, идентификатор расширения или отдельный MCP-репозиторий. Новая подсистема не должна влиять на порядок работы уже существующих возможностей.

**ID-001-11-0004** - Подключать Code Style после `registerProjectLayoutWatch` и `initWorkspaceProjects` в `bootstrapApp.ts`; если metadata adapter требует ExtensionContext, передать имеющийся объект. Инициализация не должна блокировать запуск из-за тяжёлого чтения при пустом RuleRegistry.

**ID-001-11-0005** - В `registerCodeStyleFeature` создать по одному RuleRegistry/ActionRegistry, вызвать их пустые `registerRules`/`registerActions`, собрать Settings, источники, Store, Engine, Planner/Scheduler, Dispatcher, Service, Publisher и единый координатор событий. Не создавать параллельные экземпляры в разных entry points.

**ID-001-11-0006** - Все disposable фичи добавить в `context.subscriptions` по принятому образцу bootstrap; инициализация и dispose должны быть идемпотентными в пределах активации. Повторная подписка, оставшаяся после деактивации, недопустима.

## Активация и взаимодействие с существующими сервисами

**ID-001-11-0007** - В текущем `package.json` автоактивация ориентирована на `packagedef` и выбранные команды/представления. Поддерживаемая отдельная выгрузка без `packagedef` должна активировать расширение; для этого при необходимости добавить `workspaceContains` по маркерам выгрузки, а не глобальную активацию для любого окна.

**ID-001-11-0008** - Рекомендуемые маркеры при настройке `activationEvents` - `**/Configuration.xml` для 1C:Конфигуратор и `**/Configuration.mdo` для 1C:EDT; выбирать точные поддерживаемые пути и проверить семантику glob VS Code. Не добавлять активацию каждого `.bsl` вне распознанных проектов.

**ID-001-11-0009** - Интегрироваться со штатными `projectOf`, `projectsSnapshot`/`listCandidates`, `projectRootKey`, `resolveProjectLayout`, `loadProjectMetadataTree`, `runMdSparrowParamsRead` и `onDidChangeMetadataFiles` в тех границах, которые описаны в документах `03`, `04` и `09`.

**ID-001-11-0010** - Для чтения metadata пользоваться готовыми `ensureMdSparrowRuntime` и API read-only; запрещено вызывать `runMdSparrowParamsMutation`, писать XML/MDO вручную или встраивать независимый XML-парсер в новую подсистему.

**ID-001-11-0011** - Соблюдать Workspace Trust-политику оригинального расширения: чтение метаданных штатным собственным компонентом не объявлять запрещённым без основания; любые будущие операции запуска пользовательского кода или записи должны проходить отдельную согласованную политику.

**ID-001-11-0012** - Существующие кэши md-sparrow, ProjectLayout и диагностика syntax-check продолжают работать независимо. Не создавать второй глобальный OutputChannel, отдельный npm-пакет, параллельный проектный менеджер или автономный процесс линтера.

## Порядок реализации

**ID-001-11-0013** - Сначала реализовать базовые типы, идентичность project/source/target, RuleRegistry, ActionRegistry и контракты Scope/Issue/ScanResult. От них зависят source providers, хранилище и будущие действия; не писать Engine поверх неполной модели идентичности.

**ID-001-11-0014** - Далее собрать SettingsProvider и проектный resolver; после них SourceRegistry с настоящими BSL и metadata поставщиками. Дешёвый отбор metadata по descriptor предшествует чтению подробных DTO.

**ID-001-11-0015** - Затем реализовать Engine, IssueStore и Planner/Scheduler с одним арбитром commit. Разграничение семантики full/partial и недопустимости stale должно быть согласовано **до** подключения файловых событий.

**ID-001-11-0016** - После готовности Store подключить Publisher и события файлов/проектов/настроек; затем собрать CodeStyleService и ActionDispatcher без прикладных действий. Наконец, интегрировать в bootstrap и настройки манифеста.

**ID-001-11-0017** - Если в ходе реализации обнаружилось несовпадение названных API с текущим main, агент сверяет действующий код и сохраняет архитектурное требование; при необходимости изменить договорённый контракт сообщает о причине, не подменяет его тихой импровизацией.

## Проверяемый итог и PR-дисциплина

**ID-001-11-0018** - После Task #1 обе registry пустые, реальных проблем нет, новые команды и панели отсутствуют, изменять исходники линтер не может. При этом internal scan/check и getIssues API, скоупы, события, актуальность, ошибочные и пустые исходники обрабатываются по контрактам.

**ID-001-11-0019** - При пустых реестрах не должно быть обхода файлов, чтения metadata tree, установки/запуска JRE и записей в Problems. Единственная собственная DiagnosticCollection Code Style существует и остаётся пустой.

**ID-001-11-0020** - Полная и частичная проверки, удаление, settings change, несколько проектов и поздние результаты обслуживаются согласованными механизмами Store/Scheduler. Проверка не должна удалять замечания не относящихся к её scope правил или проектов.

**ID-001-11-0021** - Реализацию проверять штатными `npm run typecheck`, `npm run lint`, `npm run compile` и `npm test`. **Перечень обязательных тестов, их сценарии, ожидаемые результаты и критерии приёмки заданы в [12-tests.md](12-tests.md)**; агент-кодер должен реализовать и запустить их по этой спецификации, а не самостоятельно проектировать тестовое покрытие. Автор оригинального репозитория требует проверок перед PR.

**ID-001-11-0022** - Для будущего PR в оригинал соблюдать [CONTRIBUTING.md](https://github.com/yellow-hammer/vscode-1c-platform-tools/blob/main/CONTRIBUTING.md), [PR template](https://github.com/yellow-hammer/vscode-1c-platform-tools/blob/main/.github/PULL_REQUEST_TEMPLATE.md) и [CI](https://github.com/yellow-hammer/vscode-1c-platform-tools/blob/main/.github/workflows/ci.yml): фокус одного PR, Conventional Commits по-русски в прошедшем времени множественного числа, документация при изменении UX; `CHANGELOG.md` вручную не редактировать.

**ID-001-11-0023** - При реализации будущих правил не требуются изменения уже готовой инфраструктуры, кроме регистрации новых SourceKind, когда появятся настоящие новые виды данных. Допускается корректировка архитектуры по результатам практики, но она должна быть осознанной, а не скрытой инициативой кодера.
