# 01 - Назначение и архитектурные границы

## Источник требований и результат

**ID-001-01-0001** - Эта спецификация детализирует [Issue #1](https://github.com/haronkz-glitch/vscode-1c-platform-tools/issues/1), а не заменяет его. Issue задаёт объём этапа, документы `02`-`11` фиксируют технические решения. При обнаружении несовместимых требований разработчик должен сообщить о противоречии, а не молча выбрать удобный вариант.

**ID-001-01-0002** - Цель Task #1 - подключённая, безопасная и расширяемая подсистема `src/features/codeStyle/` внутри существующего расширения 1C: Platform Tools. После этапа она не ищет ни одного реального нарушения, потому что оба регистра прикладных определений пусты.

**ID-001-01-0003** - В рамках этапа запрещено добавлять содержательные BSL/metadata-правила, демонстрационные правила в production, команды MCP/VS Code, панель, обработчики прикладных действий или реализацию исправлений. Будущие две проверки, MCP и UI являются независимыми последующими этапами.

**ID-001-01-0004** - Task #1 является архитектурным каркасом, но не набором мёртвых заглушек: реестры, маршрутизация, чтение источников, планирование, модель актуальности и публикация Problems должны иметь настоящую внутреннюю реализацию, пригодную для добавления правил без переписывания механики.

**ID-001-01-0005** - Соблюдать [CONTRIBUTING.md автора](https://github.com/yellow-hammer/vscode-1c-platform-tools/blob/main/CONTRIBUTING.md), [шаблон PR](https://github.com/yellow-hammer/vscode-1c-platform-tools/blob/main/.github/PULL_REQUEST_TEMPLATE.md) и текущие рабочие API исходников. Правила из среды Cursor не являются основанием менять архитектуру или навязывать дополнительные задачи.

## Границы компонентов

**ID-001-01-0006** - `CodeStyleService` - единственный фасад подсистемы и владелец её жизненного цикла. Внешние интерфейсы будущих этапов должны работать через него, а не создавать собственный движок или напрямую читать IssueStore. Внутренние зависимости передаются явно.

**ID-001-01-0007** - `RuleRegistry` хранит определения независимых правил; `ActionRegistry` хранит определения независимых операций управления. Они не связаны количеством элементов: добавление сотого правила не должно создавать новую MCP-команду, действие или UI-обработчик.

**ID-001-01-0008** - `Engine` исполняет подходящие правила над подготовленными источниками и нормализует их ответы. `SourceRegistry` и поставщики получают описание и содержимое источников. `ScanPlanner/Scheduler` отвечают за области обхода, очередь и отмену; Engine не управляет файловыми подписками.

**ID-001-01-0009** - `IssueStore` хранит замечания и служебное состояние актуальности, единолично решает, принимать ли результат. `ProblemsPublisher` только преобразует текущие данные в VS Code DiagnosticCollection и ничего не сканирует.

**ID-001-01-0010** - `SettingsProvider` предоставляет снимок настроек конкретного проекта. `ActionDispatcher` исполняет только зарегистрированные универсальные операции на ограниченном контексте сервисов, не зависит от MCP и Webview. События редактора и файлов обходят ActionDispatcher и передаются непосредственно планировщику.

**ID-001-01-0011** - Разрешённые направления зависимостей: регистрация фичи -> сервис/компоненты; планировщик -> реестр/источники/движок/хранилище; движок -> контракты и подготовленный контекст; Publisher -> хранилище; Dispatcher -> Registry и ограниченные зависимости. Обратные импорты из core в presentation, MCP, панель или bootstrap запрещены.

## Принципы расширяемости и безопасности

**ID-001-01-0012** - Для добавления правила поддерживаемого вида исходника достаточно одного модуля определения и записи в `rules/registerRules.ts`; изменения Engine, Store, SettingsProvider, панели и будущих MCP-адаптеров недопустимы.

**ID-001-01-0013** - Для добавления действия управления достаточно определения/обработчика и записи в `actions/registerActions.ts`; реестр действий не содержит специальных веток по имени действия. Доступные для новых действий общие функции предоставляются сервисами, а не дублируются.

**ID-001-01-0014** - У каждого правила независимые area (одна из пяти областей) и category (одна из шести категорий). Вид источника `SourceKind` является третьей независимой осью, не выводится из расширения файла или категории.

**ID-001-01-0015** - Чтение, сканирование, публикация и изменение состояния линтера не имеют права записывать пользовательские исходники. Даже если контракт содержит сведения об исправляемости, точку записи и применение fix в Task #1 не создавать.

**ID-001-01-0016** - Проверка с пустым реестром или без применимых активных правил завершается без сканирования каталогов, загрузки дерева, создания JVM и показов Problems. Пустое состояние является штатным, а не неисправностью.

**ID-001-01-0017** - Расширение поддерживает 1C:Конфигуратор, 1C:EDT, несколько проектов, расширения и внешние объекты в пределах возможностей существующих адаптеров. Переиспользовать WorkspaceProjects, ProjectLayout, md-sparrow и штатный logger; не вводить параллельное обнаружение проектов или XML/MDO-парсер.

**ID-001-01-0018** - Наблюдаемый результат отделять от технической ошибки: `нет нарушений` допустимо только для успешно проверенной области; сбой источника, исключение правила, отмена и неполный обход не являются успешной пустой проверкой.

**ID-001-01-0019** - Проектирование подробных тестовых сценариев не входит в эти документы: агент-разработчик самостоятельно пишет и запускает тесты по контрактам и критериям. Архитектура и поведение фиксируются здесь, имена локальных переменных и декомпозиция мелких функций остаются за реализацией.
