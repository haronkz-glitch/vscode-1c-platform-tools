# 12 - Тестирование каркаса Code Style (Task #1)

## Назначение, границы и критерий достаточности

**ID-001-12-0001** - Этот документ задаёт **обязательные проверяемые сценарии** Task #1 в дополнение к контрактам `01`–`11`. Спецификацию тестов составляет проект; агент-кодер реализует и запускает тесты по приведённым сценариям и ожидаемым результатам, а **не определяет объём тестирования самостоятельно**. Если сценарий противоречит действующему контракту или актуальному API, сообщить о расхождении, не подменять ожидаемое поведение.

**ID-001-12-0002** - Создание тестов является отдельной работой в ветке реализации (`0.1.0`); в ветке `Tasks` находятся только документы спецификации. В рамках этой работы не добавлять production-правила, MCP-инструменты, UI, CodeActionProvider или исправления исходников. Цель — подтвердить работоспособность существующего каркаса, а не разработать функции следующих задач. Основание: `ID-001-01-0002`–`0004`, `ID-001-11-0018`.

**ID-001-12-0003** - Для проверки непустых реестров использовать **только тестовые** `RuleDefinition`, `ActionDefinition`, `SourceProvider` и управляемые зависимости. Они не должны попадать в `rules/registerRules.ts` и `actions/registerActions.ts` production-сборки. В реально активированном расширении после Task #1 оба реестра остаются пустыми. Основание: `ID-001-05-0001`, `ID-001-10-0009`, `ID-001-11-0019`.

**ID-001-12-0004** - Разместить тесты в `src/test/codeStyle/`, по компонентам, с именами `*.test.ts`. Не размещать их рядом с production-кодом в `src/features/codeStyle/` и не создавать отдельное тестовое расширение, пакет или раннер. Предлагаемый состав: `registry.test.ts`, `actions.test.ts`, `projects.test.ts`, `bslSource.test.ts`, `metadataSource.test.ts`, `engine.test.ts`, `issueStore.test.ts`, `scheduler.test.ts`, `settings.test.ts`, `eventsProblems.test.ts`, `service.test.ts`. Внутри каждого файла допускаются несколько `suite` по ответственностям; объединение файлов возможно без потери сценариев.

**ID-001-12-0005** - Повторять стиль автора оригинального Platform Tools: TypeScript, `suite()` / `test()`, `node:assert` (`strictEqual`, `deepStrictEqual`, `rejects` и т. п.), названия на русском, один сценарий — одно наблюдаемое поведение. Использовать `setup/teardown` для изоляции состояния и существующие помощники в `src/test/fixtures/helpers/`, а не новый фреймворк. Файлы `*.test.ts` выполняются через существующий VS Code Extension Host (`.vscode-test.mjs`).

**ID-001-12-0006** - Объём — ориентировочно **11 тестовых файлов и 55 сценариев** ниже, а не формальное требование процента покрытия. Один `test()` может проверять несколько близких вариантов одного поведения, если при падении понятна причина. Не дробить единый смысловой сценарий ради счётчика и не опускать обязательные ожидаемые результаты ради уменьшения числа тестов. Дополнительные сценарии допускаются только для конкретного обнаруженного дефекта или существенной непроверенной ветки контракта, без массового «тестирования каждой строки».

**ID-001-12-0007** - Все проверки должны быть детерминированными, изолированными и не менять рабочие проекты пользователя. Подменять внешние вызовы md-sparrow, файловые события, таймеры и длительные асинхронные операции управляемыми зависимостями либо существующими тестовыми средствами. Для конкурентных сценариев использовать контролируемое завершение Promise, а не произвольные `sleep` и долгие ожидания. Не требовать установленной платформы 1С, реальной JVM, реального MCP-сервера, доступа к сети или GitHub во время выполнения тестовых сценариев.

**ID-001-12-0008** - Компактные предметные входные данные размещать в `src/test/fixtures/codeStyle/`, если они не являются тривиальными скалярами. По возможности брать реальные фрагменты уже имеющихся тестовых выгрузок EDT/Конфигуратора и образцы DTO, а не выдуманные большие графы. Для новых внешних фикстур документировать происхождение, назначение и способ регенерации в `README.md`; изменчивые пути заменять стабильными значениями, использовать существующий `fixturePath`. Временные каталоги очищать в `teardown`. Для элементарных pure-unit тестов допустимы небольшие литералы — согласно правилам автора о фикстурах.

**ID-001-12-0009** - Проверять публичные/внутренние контракты компонентов, а не приватные поля, точную последовательность внутренних вызовов без требований или косметические детали реализации. Интеграционные сценарии должны проходить через реальные компоненты там, где это возможно; тестовые doubles допустимы на границе внешней системы. Не менять production-архитектуру только для получения удобного тестового крючка; при необходимости узкого внедрения зависимости обосновать минимальную правку.

**ID-001-12-0010** - Ниже каждый пункт обозначает один смысловой сценарий с ожидаемым результатом. Ссылки на `ID-001-XX-YYYY` показывают, какой исходный контракт он подтверждает. Тестировщик может объединить совместимые проверки в одном `test()`, но обязан сохранить все перечисленные исходы.

## Фикстуры, запуск и приёмка

**ID-001-12-0066** - Использовать минимальные наборы: проект/кандидат и вложенный проект, BSL с `Ext`/BOM/CRLF, корневой и дочерний metadata descriptor для EDT/Конфигуратора, один компактный DTO и тестовый Issue с реальным диапазоном. Если образец уже присутствует в `src/test/fixtures/`, использовать его повторно. Не копировать всю конфигурацию, многомегабайтный ответ md-sparrow или сотни дублирующих примеров.

**ID-001-12-0067** - Моки должны фиксировать **проверяемые побочные эффекты**: число `enumerate/read`, число запусков runtime, попытки `mutation/write`, публикацию/очистку DiagnosticCollection, отмену и события. В тестах гонок явно контролировать, какой Promise завершается раньше. Использовать настоящие `IssueStore`/`Engine` там, где их состояние является предметом проверки; не заменять проверяемую реализацию мок-объектом.

**ID-001-12-0068** - Убрать за тестами все изменённые VS Code настройки, временные папки, глобальные состояния и обработчики событий. Сценарии должны проходить независимо от порядка запуска; тесты не должны зависеть от наличия соседней выгрузки на компьютере разработчика, абсолютного пути Windows или живой базы 1С. Для требований, зависящих от ОС, проверять соответствующую ветвь на подходящей платформе, не объявлять другую ОС неисправной.

**ID-001-12-0069** - Подключение к инфраструктуре автора: `npm run typecheck`, `npm run lint`, `npm run compile`, `npm test`. Существующая `.vscode-test.mjs` обнаруживает `out/test/**/*.test.js`, а `esbuild.config.mjs` собирает `src/test/**/*.test.ts`. Не менять `test:node`, CI или зависимости ради этого набора без технической необходимости. Оригинальный CI выполняет Extension Host-тесты на Linux через `xvfb-run`; отдельные Node-тесты на Windows/macOS относятся к другим компонентам и не являются обязательной новой матрицей для Task #1.

**ID-001-12-0070** - Приёмка считается успешной, когда все обязательные наблюдаемые результаты выше подтверждены автоматизированными проверками, штатные команды завершаются без ошибок и после прогона не остаётся изменённых исходников/настроек. Отдельно подтвердить критический минимум: пустые реестры не запускают анализ, старый `full` не перезаписывает свежий `partial`, соседние пары сохраняются, stale немедленно исчезает из Problems, а проверка ничего не записывает.

**ID-001-12-0071** - В отчёте о реализации тестов указать пути файлов, результат запуска команд, количество фактически написанных сценариев и причины любого сознательного отклонения от требований `ID-001-12-*`. Не выдавать непроверенный сценарий за выполненный. В случае невозможности достоверно проверить конкретное требование сообщить об этом отдельно, а не подменять тест утверждением о корректности.

**ID-001-12-0072** - Документ **не** требует тестировать ещё не созданные `common-module-type`, `block-blank-lines`, `assignment-alignment`, внешние `codeStyle.*` MCP-команды, пользовательскую панель, auto-fix и работу реальной 1С. Они получат собственные сценарии в следующих задачах. Изменять ранее утверждённые контракты `01`–`11` ради удобства теста запрещено без согласования.
